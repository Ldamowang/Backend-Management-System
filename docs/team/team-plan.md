# 后台管理系统 -- 4人团队组建方案

## 一、角色职责与技能要求

### 1.1 产品经理 (PM)

**核心职责：** 需求的源头和验收的终点，负责"做什么"和"做得对不对"。

| 职责领域 | 具体内容 |
|---------|---------|
| 需求管理 | 编写/维护 PRD，拆解用户故事，定义验收标准 |
| 权限设计 | 维护 RBAC 权限矩阵，新增角色时更新 |
| 优先级仲裁 | Bug 定级（P0-P3）、需求排序、变更控制 |
| 验收把关 | 使用验收 Checklist 逐项签字 |
| 跨角色协调 | 组织评审会议、解决前后端分歧、推进阻塞问题 |
| 文档输出 | 用户手册、上线公告、版本变更日志 |

**技能要求：**
- 必须：PRD 写作能力、RBAC 权限模型理解、原型工具（Figma/Axure）、项目管理工具使用
- 加分：了解 RESTful API 设计、能看懂 Swagger 文档、有后台管理系统产品经验
- 软技能：逻辑清晰、沟通协调能力强、有优先级判断力

### 1.2 后端开发

**核心职责：** 系统的"骨架和安全线"，负责 API、数据库、认证鉴权、性能。

| 职责领域 | 具体内容 |
|---------|---------|
| API 开发 | Spring Boot 3.2 + MyBatis-Plus，RESTful 接口实现 |
| 安全加固 | Spring Security 6 + JWT 认证、`@PreAuthorize` 权限注解、XSS 过滤、接口限流 |
| 数据库设计 | MySQL 8 表结构维护、SQL 性能优化、Redis 缓存策略 |
| API 文档 | Swagger/OpenAPI 注解，作为前后端协作的契约 |
| 测试 | JUnit 5 单元测试 + Controller 集成测试，覆盖率目标 >= 80% |
| 部署 | Docker 镜像构建、docker-compose 配置维护 |

**技能要求：**
- 必须：Java 17、Spring Boot 3.x、Spring Security 6、MyBatis-Plus、MySQL 8、Redis、JWT、JUnit 5
- 加分：Docker、Nginx 配置、JMeter/k6 性能测试、CI/CD 配置经验
- 素质：安全意识强（本系统涉及认证鉴权）、重视测试、API 设计规范

### 1.3 前端开发

**核心职责：** 系统的"面子"，负责界面交互、状态管理、权限控制的前端实现。

| 职责领域 | 具体内容 |
|---------|---------|
| 页面开发 | Vue 3 + TypeScript + Element Plus |
| 状态管理 | Pinia Store（user/app/permission 三个模块） |
| 权限控制 | 动态路由生成、`v-permission` 指令 |
| API 对接 | Axios 请求封装、Token 自动刷新拦截器 |
| 组件开发 | Layout 组件（Sidebar/Header/Breadcrumb）、通用业务组件 |
| 测试 | Vitest 单元测试 + 组件测试 |
| 性能 | 路由懒加载、打包分析、首屏优化 |

**技能要求：**
- 必须：Vue 3 Composition API、TypeScript、Element Plus、Pinia、Axios、Vue Router 4、Vite
- 加分：Vitest + Vue Test Utils、Playwright E2E、SCSS、响应式布局、前端性能优化
- 素质：注重交互细节、TypeScript 类型安全意识、组件化思维

### 1.4 测试工程师 (QA)

**核心职责：** 质量的"守门人"，覆盖从单元到 E2E 的全链路质量保障。

| 职责领域 | 具体内容 |
|---------|---------|
| 测试策略 | 维护测试策略文档 |
| API 测试 | Postman Collection，覆盖全部权限标识对应的接口，正向 + 反向 |
| E2E 测试 | Playwright 自动化，覆盖登录、CRUD、权限拦截、Token 刷新等核心场景 |
| 安全测试 | SQL 注入、XSS、越权访问、Token 伪造、接口限流 |
| 性能测试 | JMeter/k6 并发测试、Lighthouse 前端性能 |
| Bug 管理 | 提交规范 Bug 报告、跟踪修复状态、回归验证 |
| 质量报告 | 输出测试覆盖率报告、Bug 统计分析、准出评审意见 |

**技能要求：**
- 必须：测试用例设计、Postman API 测试、Bug 管理工具、基本的 SQL 能力
- 加分：Playwright 自动化、JMeter/k6 性能测试、OWASP 安全测试基础、CI 集成测试
- 素质：细致严谨、善于发现边界问题、能独立搭建测试环境

## 二、团队协作流程

### 2.1 完整的需求到上线流程

```
 需求提出         需求评审          API 契约定义        并行开发
 ─────────────────────────────────────────────────────────────
 PM 编写          全员参与          后端输出 Swagger     前端：页面开发
 用户故事          评估可行性        前端评审确认         后端：接口开发
 验收标准          排期估点          达成一致             各自单元测试
      │               │                │                    │
      ▼               ▼                ▼                    ▼
    联调对接         测试验证         Bug 修复           验收上线
 ─────────────────────────────────────────────────────────────
 前后端联调         QA 执行          开发修复             PM 验收签字
 问题修复           API + E2E        QA 回归验证          部署上线
                   安全 + 性能       PM 确认关闭          线上冒烟
```

### 2.2 关键协作节点

**节点 A：API 契约先行（后端 → 前端）**
- 后端先设计 Swagger 文档，定义请求/响应格式
- 前端基于 Swagger 同步开发 API 调用层
- 双方就字段命名、分页格式、错误码达成一致后再各自编码
- 契约变更必须通知对方并更新文档

**节点 B：权限矩阵驱动（PM → 后端 + 前端）**
- PM 在权限矩阵中定义每个功能的权限标识
- 后端据此添加 `@PreAuthorize("hasAuthority('sys:user:add')")` 注解
- 前端据此使用 `v-permission="['sys:user:add']"` 指令
- QA 据此编写越权测试用例

**节点 C：Bug 闭环流程**

```
QA 发现 Bug → 提交 Bug 报告（含复现步骤） → PM 定优先级 →
分配给对应开发 → 开发修复并自测 → QA 回归验证 →
PM 确认关闭（P0/P1）或留下迭代（P3）
```

**优先级定义：**
- **P0（阻塞）**：系统无法启动、登录崩溃、数据丢失 → 立即修复
- **P1（严重）**：核心功能异常、权限绕过、数据错误 → 当天修复
- **P2（一般）**：交互异常、样式问题 → 3 天内修复
- **P3（建议）**：体验优化、文案调整 → 下一迭代

### 2.3 Git 分支规范

| 分支 | 用途 | 谁操作 |
|------|------|--------|
| `main` | 生产代码，受保护 | 仅通过 PR 合入 |
| `develop` | 开发主干 | 前端、后端日常合入 |
| `feature/xxx` | 功能分支，如 `feature/user-export` | 前端或后端从 develop 拉出 |
| `fix/xxx` | Bug 修复分支 | 对应开发者 |
| `release/v1.x` | 发布分支 | 后端负责，QA 在此分支做最终验证 |

**提交格式：** `<type>: <description>`，type 包括 feat / fix / refactor / docs / test / chore / perf / ci

## 三、各阶段工作内容

### 第一阶段：需求确认与基础完善（第 1-2 周 / 里程碑 M1）

| 角色 | 具体任务 | 产出物 |
|------|---------|--------|
| **PM** | 完善 PRD v1.0；细化权限矩阵；编写验收 Checklist；组织需求评审会 | PRD 终稿、权限矩阵终稿、验收标准 |
| **后端** | 补充 `@PreAuthorize` 注解；完善异常处理；补充 Swagger 注解；确认 Redis 缓存策略 | 权限完整、API 文档、安全基线 |
| **前端** | TypeScript 类型审查；确认动态路由与权限矩阵一致；全局错误边界；统一 SCSS 变量和主题 | 类型安全、UI 规范统一 |
| **QA** | 完善测试策略文档；搭建 Playwright 环境；编写 Postman Collection；准备测试数据 | 测试计划、测试环境、基础测试数据 |

**M1 交付标准：**
- [ ] PRD v1.0 终稿评审通过
- [ ] 权限矩阵终稿，后端全部接口已加 `@PreAuthorize`
- [ ] Swagger API 文档完整覆盖所有接口
- [ ] 前端 TypeScript 类型安全，零 any 泄漏
- [ ] QA 测试环境搭建完成，Postman Collection 基础版就绪

### 第二阶段：核心功能完善与测试（第 3-4 周 / 里程碑 M2）

| 角色 | 具体任务 | 产出物 |
|------|---------|--------|
| **PM** | 验收 M1 产出；定义增强需求（导出 Excel、批量操作）；UX 走查 | M1 验收报告、增强需求文档 |
| **后端** | 数据导入导出功能；补充 Controller 层集成测试；N+1 查询优化 | 功能完善、覆盖率 >= 60% |
| **前端** | 对接导出功能；骨架屏/空状态组件；核心页面组件测试 | 交互优化、测试补充 |
| **QA** | API 接口全覆盖测试；E2E 核心路径（登录、用户 CRUD、权限拦截）；安全测试 | 接口测试报告、E2E 脚本、安全测试报告 |

**M2 交付标准：**
- [ ] 所有 P0 + P1 功能开发完成
- [ ] 后端单元测试覆盖率 >= 60%
- [ ] API 接口测试覆盖率 100%（正向）
- [ ] E2E 覆盖 3 个 P0 场景
- [ ] 零 P0 Bug，P1 Bug <= 3

### 第三阶段：集成联调与质量冲刺（第 5-6 周 / 里程碑 M3）

| 角色 | 具体任务 | 产出物 |
|------|---------|--------|
| **PM** | 全流程端到端验收；完善用户操作手册；制定上线 Checklist | 全流程验收报告、操作手册 |
| **后端** | Bug 修复；集成 Actuator 监控；Docker 镜像优化 | Bug 清零、监控就绪、覆盖率 >= 80% |
| **前端** | Bug 修复；性能优化（懒加载、打包分析）；兼容性测试 | Bug 清零、性能达标、覆盖率 >= 80% |
| **QA** | 全量回归测试；性能测试（100 并发 < 2s、万条分页 < 500ms）；最终质量报告 | 回归报告、性能报告、上线许可 |

**M3 交付标准：**
- [ ] 前后端单元测试覆盖率 >= 80%
- [ ] E2E 覆盖全部 7 个核心场景
- [ ] 安全测试 5 项全部通过
- [ ] 性能测试达标（100 并发 < 2s、万条分页 < 500ms、Lighthouse >= 80）
- [ ] 零 P0/P1 Bug，P2 Bug < 5

### 第四阶段：上线部署与运维交接（第 7 周 / 里程碑 M4）

| 角色 | 具体任务 |
|------|---------|
| **PM** | 上线公告撰写、用户培训材料、下一版本 Backlog 整理 |
| **后端** | 生产环境部署（docker-compose up）、监控告警配置、运维文档、数据库备份策略 |
| **前端** | CDN 配置、Nginx 静态资源缓存优化、前端错误监控（如 Sentry）集成 |
| **QA** | 线上冒烟测试、监控大盘验证、线上 Bug 快速响应 |

**M4 交付标准：**
- [ ] 生产环境 Docker 部署成功
- [ ] 线上冒烟测试通过
- [ ] 监控告警配置完成
- [ ] 运维文档和用户手册交付

### 4.3 信息同步规则

- **需求变更**：PM 在项目管理工具中更新，并在群里 @全员通知，附变更原因和影响范围
- **API 变更**：后端在 Swagger 更新后，在群里 @前端 + @QA，说明新增/修改/废弃的接口
- **阻塞问题**：任何人发现阻塞问题，15 分钟内在群里反馈，PM 协调解决
- **代码合并**：所有 PR 必须至少 1 人 Review 后才能合入 develop
- **测试报告**：QA 每周五在群里发布本周测试总结（新增 Bug 数、修复率、覆盖率）

## 五、迭代计划

### 5.1 总体时间线（7 周）

```
W1        W2        W3        W4        W5        W6        W7
├─────────┼─────────┼─────────┼─────────┼─────────┼─────────┤
│  M1：需求确认 &   │  M2：功能完善 &   │  M3：质量冲刺 &   │ M4：上线 │
│  基础完善          │  测试覆盖          │  性能优化          │ 部署     │
├─────────┼─────────┼─────────┼─────────┼─────────┼─────────┤
  Sprint 1            Sprint 2            Sprint 3           Sprint 4
  (2周)               (2周)               (2周)              (1周)
```

### 5.2 迭代节奏

采用 **2 周一个 Sprint** 的敏捷节奏：

```
Sprint 规划 (周一上午 2h)
  ↓
每日站会 (15min)
  ↓
Sprint 中期检查 (第 2 个周三)
  ↓
Sprint 评审/Demo (第 2 个周五上午)
  ↓
Sprint 回顾 (第 2 个周五下午)
```

每个 Sprint 的用户故事由 PM 在 Sprint 规划会上排入，使用 **故事点估算**（Fibonacci：1/2/3/5/8/13），每人每 Sprint 承载约 20 个故事点。

## 六、风险识别与应对

### 6.1 人员风险

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| 单人负责全部后端/前端，无备份 | 高 | 高 | 关键代码必须有文档注释；PR 需另一角色 Review；知识沉淀到文档 |
| 某角色请假/离职 | 中 | 高 | 所有知识沉淀到文档；Git 提交信息详细；提前建立外部技术支援渠道 |
| 技能不匹配 | 中 | 中 | 招聘时严格按技能要求筛选；第一周安排技术栈熟悉时间 |

### 6.2 技术风险

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| 前后端接口不一致 | 高 | 中 | API 契约先行；前端用 Mock 并行开发；联调阶段预留 2-3 天缓冲 |
| 权限模型实现与设计不一致 | 中 | 高 | 权限矩阵作为 Single Source of Truth；QA 编写越权测试 |
| JWT Token 刷新并发问题 | 中 | 高 | Axios 拦截器使用请求队列；后端刷新接口加锁或幂等处理 |
| MySQL 大数据量分页性能 | 低 | 中 | 使用 MyBatis-Plus 分页插件；关键字段加索引；万条数据性能测试 |

### 6.3 流程风险

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| 需求频繁变更 | 高 | 高 | Sprint 内冻结需求；新需求进 Backlog；紧急变更需全员确认 |
| 测试发现问题太晚 | 中 | 高 | QA 从 M1 就介入；开发自测后再提交 QA；每个 Sprint 含测试 |
| 上线部署失败 | 低 | 高 | M2 开始用 Docker 部署到测试环境；准备回滚方案；上线前预演 |

### 6.4 小团队特殊风险

| 风险 | 应对 |
|------|------|
| 沟通过载 | 严格控制会议时长，其余用异步沟通 |
| 质量与速度矛盾 | 优先保障核心路径测试；利用 AI 辅助生成测试代码 |
| 前后端独立开发致集成风险 | 每周至少 1 次联调验证；M2 中期安排完整联调 |

## 八、核心原则

1. **文档驱动** -- 4 人小团队没有冗余人力，知识必须沉淀到文档中，不能依赖口头传达
2. **契约先行** -- API Swagger 文档是前后端协作的基石，先定契约再并行开发
3. **质量左移** -- QA 从第一周就介入，不要等到开发完再集中测试
4. **渐进交付** -- 每个 Sprint 都有可验收的产出，不追求一次性完美
5. **风险前置** -- 权限模型、Token 刷新、接口一致性等高风险点在 M1 就要解决
